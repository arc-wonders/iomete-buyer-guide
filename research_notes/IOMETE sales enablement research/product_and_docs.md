## Key Question 1: Exact product definition, tagline, and main components

### Takeaway
IOMETE positions itself as "The sovereign data platform" / "The Sovereign Data Lakehouse Platform": a self-hosted, Kubernetes-native data lakehouse built on Apache Spark and Apache Iceberg that runs on-premises, in the customer's cloud, hybrid, or air-gapped. Components are compute clusters (SQL endpoints), Spark jobs, Spark Connect, Jupyter containers, event streams, SQL editor with dashboards, data catalog, data security (Ranger-style policies), identity (SSO/LDAP), job orchestrator (Prefect), Iceberg REST catalog, and (beta) MCP server and automated table maintenance.

## Key Question 2: Deployment models and infrastructure requirements

### Takeaway
Documented deployment: any Kubernetes (on-prem, EKS/AKS/GKE, OpenShift/VMware Tanzu, Nutanix NKP, k3s for POC), with object storage (S3, Azure Blob, GCS, Ozone, Dell ECS, MinIO, IBM COS, any S3-compatible), PostgreSQL metadata DB, Istio ingress (Traefik on NKP), installed by Helm chart `iomete/iomete-data-plane-enterprise` (version 3.19.1 example; platform now at 4.0.1). Air-gapped is claimed on marketing pages and FAQ but no dedicated air-gapped install guide was found. Minimums: 12 CPU/24 GB for platform services plus a 4 CPU/32 GB node for Spark; sizing guide recommends 1 CPU : 8 GB RAM and local SSD for shuffle.

### Cited Findings

**Deployment models**

- Blog "IOMETE Deployment Models" (published Feb 10, 2025, author Vusal Dadalov, founder; last updated Oct 1, 2026): on-prem, private cloud, public cloud (AWS, Azure, GCP; also lists Oracle Cloud Infrastructure, IBM Cloud, Digital Ocean, regional providers), hybrid/multi-cloud (control plane manages multiple data planes), air-gapped mentioned only in a callout; storage: NFS and S3-compatible. — [Deployment models blog](https://iomete.com/resources/blog/iomete-deployment-models)

**Infrastructure requirements (install guide)**

- Storage types: `s3_compatible` storage type added in 3.19.1; `storage.minioSettings` and `storage.dellEcsSettings` deprecated. — [Release notes](https://iomete.com/resources/deployment/on-prem/release-notes/), [Deployment Architecture](https://iomete.com/resources/deployment/architecture-deployment)

- Scalability page: cloud autoscalers supported (AWS Karpenter, GKE Node Auto-Provisioning, AKS Cluster Autoscaler); on-prem node pool scaled manually; HPA disabled by default for most services (only `iom-event-stream-proxy` on by default, 1–4 replicas at 80% CPU); `iom-sql` does not support HPA (fixed single replica); executor autoscaling via Spark dynamic allocation starting at one executor and scaling to zero when idle; single-node (driver-only) mode available; priority classes `iomete-compute`, `iomete-spark-job`, `iomete-notebook`, `iomete-operational-support`; storage backends Amazon S3, GCS, ADLS, Apache Ozone, Dell ECS, MinIO; spot instances "up to 3x cost reduction". — [Scalability](https://iomete.com/resources/getting-started/scalability)
- Spark executor shuffle storage options page and EMPTY_DIR "Reserve capacity on the node" option (v3.19.0) exist. — [Docs sitemap](https://iomete.com/resources/sitemap.xml), [Release notes](https://iomete.com/resources/deployment/on-prem/release-notes/)
- GitHub `iomete-deployment` repo folders: `.github/workflows`, `aws/data-plane-helm`, `database`, `gcp/data-plane-helm`, `istio-ingress`, `kubernetes`, `minio`, `on-prem`, `ozone`, `terraform`, plus `iomete-crds.yaml`, `service-account.yaml`, `spark-operator-webhook-template.yaml`; 45 commits; no README description. — [github.com/iomete/iomete-deployment](https://github.com/iomete/iomete-deployment)

### Inferences
- A supported Kubernetes version range is not published anywhere found; the product likely relies on whatever the Spark Operator and Istio versions in the chart support.
- "Air-gapped" is a marketing/FAQ claim; the install guide only hints at it via `docker.imagePullSecrets` and the private Docker registry page, implying images must be mirrored to a private registry.
- The two install flows (Helm chart via chartmuseum.iomete.com vs. Terraform for Azure only) suggest Azure is the most automated cloud path, with AWS/GCP handled via the `aws/data-plane-helm` and `gcp/data-plane-helm` folders.

### Gaps
- No published supported Kubernetes version matrix, OpenShift-specific guide, or dedicated air-gapped install guide found.
- Container image registry location (for mirroring) not captured.
- No statement found on IOMETE-hosted/SaaS option (license agreement explicitly says not SaaS).

## Key Question 3: Architecture (Spark, Iceberg, Kubernetes, catalog, control plane vs data plane)

### Takeaway
IOMETE deploys as one Helm chart into a Kubernetes namespace; a set of microservices (Gateway/Nginx, Core, Cluster, Identity, SQL, Catalog, Iceberg REST Catalog, Health Check, Socket, Collaboration, Prefect orchestrator, Spark Operator, Spark History Server, Typesense search) sit over PostgreSQL and object storage, and dynamically create Spark driver/executor pods for compute clusters, Spark jobs, Jupyter containers, and event streams. The native catalog is an Iceberg REST Catalog with Ranger-style policy enforcement. A formal control-plane / multi-data-plane split shipped in v4.0.0 (Sep 30, 2026); the older multi-cluster doc (3.16.x) still says there is "no unified control plane".

### Cited Findings
- Architecture page: platform built on Apache Spark, Apache Iceberg, Kubernetes; deploys as a Helm chart; three tiers (infrastructure = Kubernetes + object storage; platform microservices; on-demand Spark workloads); all services in a single namespace with optional multi-namespace for Spark workloads; compute and storage decoupled. — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Metadata: one PostgreSQL server; separate databases auto-created for Hive Metastore, Ranger policies, Iceberg catalog, and each microservice. — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Services: IOMETE Gateway (Nginx reverse proxy routing API, UI, Spark Connect, Arrow Flight, WebSocket, gRPC); Core Service (data plane and system config, tokens, authorization checks, node types, volumes, Spark settings, S3 browser, Spark History Server proxy); Cluster Service (compute clusters, Spark batch/streaming jobs, Jupyter containers, Docker registries, namespaces, secrets, event stream definitions); Identity Service (users, groups, roles, LDAP, SAML, OIDC, Apache Ranger policy management, bundle-based authorization); SQL Service (SQL execution, worksheets, workspaces, Git, query history, database explorer, dashboards); Catalog Service (full-text search backed by Typesense, table metadata, classification tags, access permissions); Iceberg REST Catalog Service (implements Iceberg REST Catalog spec; every request checked against Apache Ranger policies); Health Check Service (every 10 s, 48 h history). — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Spark infrastructure: Spark Operator (controller for SparkApplication CRDs, webhook, Submit Service with queueing); internal Spark Connect cluster for metadata extraction (not user-facing); Spark History Server reading event logs from object storage. — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Workloads: Compute Clusters = Spark driver pods exposing HiveServer2 (port 10000), Spark Connect (15002), Arrow Flight (33333 when enabled); Spark Jobs (batch/streaming, Scala or PySpark, scheduled via Job Orchestrator); Jupyter Containers (JupyterLab pods via Gateway); Event Streams (HTTP POST ingestion into Iceberg, powered by "Papyrus (Rust)", admin must enable). — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Security: authentication via built-in username/password, LDAP, or SSO (SAML, OIDC); authorization at three levels: platform (Core Service), data (Ranger policies enforced by Iceberg REST Catalog for row filtering, column masking, table permissions), resource (Resource Access Service with VIEW/UPDATE/MANAGE). — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Real-time/orchestration: Socket Service (WebSocket); Collaboration Service (CRDT-based real-time SQL editing, feature-flagged); NATS JetStream (cross-pod sync, optional); Job Orchestrator = Prefect Server + Prefect Workers per namespace. — [Architecture](https://iomete.com/resources/getting-started/architecture)
- Deployment Architecture page: `controlPlaneNodeSelector`/`controlPlaneTolerations` apply to platform services; `dataPlaneNodeSelector`/`dataPlaneTolerations` apply to Spark drivers/executors; data-plane config stored in Kubernetes Secret `data-plane`; service endpoints `cc-<name>.<ns>:15002` (Spark Connect), `:10000` (HiveServer2 JDBC over HTTP), `:33333` (Arrow Flight), `jc-<name>.<ns>:8888` (Jupyter); extra namespaces each get a Prefect Worker and optionally Spark Proxy Server and Event Stream pods; `clusterDatabase` can point to a different PostgreSQL than `database`; Typesense 20Gi PVC; NATS 3 replicas; Event Stream 2 replicas; about 30 services listed. — [Deployment Architecture](https://iomete.com/resources/deployment/architecture-deployment)
- Multi-cluster setup page (introduced "Version 3.16.x"): three topologies (single installation; multiple independent installations; multi-cluster with shared global database). Global DBs: `iomete_catalog_db`, `iomete_iam_db`, `iomete_iceberg_db`, `iomete_metastore_db` (services iom-catalog, iom-core, iom-identity, iom-rest-catalog, metastore); cluster-local DBs: `iomete_prefect_db`, `iomete_sql_db` (iom-cluster, iom-sql, prefect-server, prefect-worker). Stated limitation: "This implementation does not provide a unified control plane or a single view across instances." A single control plane architecture is "planned for a future release". — [Multi-Cluster Setup](https://iomete.com/resources/deployment/multi-cluster-setup)
- v4.0.0 release notes (Sep 30, 2026): "Multi-cluster support: The platform splits into one control plane and one or more data planes", with Data Planes admin page, remote workloads, per-plane health checks, plane-to-plane trust, and active-active control planes. — [Release notes](https://iomete.com/resources/deployment/on-prem/release-notes/)
- v2.0.0 release notes (Oct 7, 2024): Keycloak and Ranger removed as separate components and functionality moved into IOMETE; adds tag-based access and masking and an integrated Iceberg REST Catalog; not backward compatible with 1.22.0 or earlier. — [Release notes](https://iomete.com/resources/deployment/on-prem/release-notes/)
- Spark image 3.5.7-v7 notes "Ranger upgraded to 2.8.0" (Ranger plugin inside the Spark image). — [Spark release notes](https://iomete.com/resources/deployment/on-prem/release-notes/spark)
- Hive Metastore upgraded to Hive 4.0.0 in v3.16.0 (Feb 9, 2026). — [Release notes](https://iomete.com/resources/deployment/on-prem/release-notes/)
- Catalog types: IOMETE-managed Iceberg REST Catalog (external access at `/catalogs/<catalog name>`, PAT or session auth, credential vending and remote signing) and Enterprise Catalog (auto-configured for internal workloads); external catalogs: JDBC, REST Iceberg, AWS Glue Iceberg, Nessie Iceberg; default `spark_catalog`. — [Spark Catalogs overview](https://iomete.com/resources/user-guide/spark-catalogs/overview)
- Marketing architecture section lists four pages: Open source, Apache Iceberg, Apache Spark, Data mesh, Data security, Integrations & ecosystem. — [iomete.com](https://iomete.com/)

### Inferences
- "Ranger" in IOMETE post-v2.0.0 refers to the Ranger policy model and Spark Ranger plugin embedded in IOMETE services/images, not a standalone Apache Ranger admin deployment (v2.0.0 said Ranger was "removed", yet architecture and Spark release notes continue to reference Ranger policies and plugin versions).
- Hive Metastore still exists inside the platform (database created; upgraded to Hive 4.0.0), presumably backing `spark_catalog` and HiveServer2 compatibility, while the Iceberg REST Catalog is the governed path.
- Docs contradiction: the Multi-Cluster Setup page (3.16.x, "no unified control plane") appears outdated relative to v4.0.0 release notes that ship a control-plane/data-plane split. The sales tool should prefer the release notes and flag the page.

### Gaps
- No published architecture diagram content (only alt text "IOMETE Architecture High-Level Overview" and "z100").
- No dedicated doc page found yet for the v4.0 control plane / data plane registration and trust model (release notes only).

## Key Question 8: Explicit limitations, "not supported", "coming soon", and contradictions

### Takeaway
The docs are fairly explicit about limits in release notes, the Spark 4 page, table maintenance, multi-cluster, and drivers. Several contradictions exist between marketing pages, FAQ, llms.txt, and docs (cost-savings figures, lineage, dbt adapter, control-plane status, edition naming, dead docs domain).

### Cited Findings

**Explicit limitations / not supported**
- Terraform "currently available for Azure" only. — [Install](https://iomete.com/resources/deployment/on-prem/install)
- Helm-created cluster resources unavailable on chart 3.19.0 or earlier; Helm 4 fails if existing CRD differs; CRDs never updated by `helm upgrade`. — [Install](https://iomete.com/resources/deployment/on-prem/install)
- Multi-cluster (3.16.x): "does not provide a unified control plane or a single view across instances"; global DB outage affects all instances. — [Multi-Cluster Setup](https://iomete.com/resources/deployment/multi-cluster-setup)

- Table Maintenance (Beta): "Not every catalog supports automated maintenance" (ICEBERG/REST/INTERNAL only); `spark_catalog` excluded; "Enabling table maintenance while catalog maintenance is disabled is not allowed." — [Table Maintenance](https://iomete.com/resources/user-guide/table-maintenance/overview)
